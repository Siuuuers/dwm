## Untested ordinary acceptance boundary

At product83da `tools/testing/Invoke-ExportedGameplay.ps1:143–154`, Wait-One checks its stopwatch only at loop entry. It then calls Window and Find and returns a unique match without another elapsed-time check. Thus a call that begins inside the budget can return a late match as success. This is source-demonstrable; no claim is made that it caused any retained failed run.

Existing isolated diagnostic deadline qualification already distinguishes late root acquisition from late enumeration. The ordinary function has not inherited that behavior. The proposed copy changes only Wait-One:

1. After Window returns, refuse if the budget expired, before any enumeration.
2. After Find returns, refuse if expired, before accepting or interpreting its matches.
3. Require remaining budget directly on the unique-match return.

Two existing-format Record calls identify `window` versus `find` deadline expiration. They add no provider read, tree traversal, game hook or new instrumentation subsystem. In-budget ambiguity, provider exception propagation, returned-object identity and query order remain unchanged. At an expired deadline, timeout wins over interpreting late matches, including late ambiguity.

This rejects late observations; it cannot interrupt a blocking UIA call at exactly30 seconds. The outer watchdog remains necessary. Defaults30s/480s are unchanged. No retry, alternate selector, broad enumeration, quiet wait or relaxed PID/visibility condition is introduced.
