# Save9 Load: static validation caller map

Read-only source audit of `dwm-prepare` at `12b259ee0dee26b54c002e5db9460a667cef80e5`. No local Godot/PowerShell execution. This maps reachable call sites, not the nine occurrences in an earlier timing record. The ordinary first-attempt path and recovery branches are distinguished below.

The shared document chain is `SaveDocumentSchema.validate -> _validate_document -> _validate_bundle -> RunSnapshotSchema.validate`. For Save9, each admitted historical bundle can also reach `_validate_bundle` through `_scene_journal_error`; newly written saves have an empty recovery journal. Full-schema observations must not be confused with the recursive `_validate_scene_reading` calls inside a single schema validation.

## Conditional/recovery paths

- `DesktopContinuationOperationJournal._load_owned -> storage.reconcile(_parse_document) / _validate_document -> _validate_operation -> _validate_kind_fields -> _validate_scene_source ->` document chain can validate stored scene-restore operations. This is physical recovery/adoption; it is not unconditionally executed on every `get_operation`. `_load` returns immediately when already loaded. Special creation-storage recovery uses the retained envelope path instead of full source admission.
- `_resume_operation -> _resume_restore -> _reconstruct_restore_materials -> _selected_scene_restore_bundle` revalidates the retained source after uncertain commit, pending-operation recovery, or restart. Reconstruction then calls `_prepare_bundle_with_all_participants` without same-call admission material, so run, terminal narrative and generic seed checks can recur. Identity allocation preparation subsequently reloads the retained source through `load_restore_context` again. Do not label these normal first-attempt duplicates.
- `reconcile_startup -> load_restore_context` is another retained-source recovery entry.
- `capture_committed_scene_restore -> _selected_scene_restore_bundle` explicitly validates the completed source when this diagnostic/public capture API is called. It is not automatically part of every normal Load.
- Journal `_write` already reuses validated exact text through `_parse_known_document`; forward `advance` constructs legal transitions. A journal write/advance does not imply a fresh full Run validation on every step.
- `CheckpointJournal.prepare_record`, `prepare_reset_with_initial` and `remember_written_retained_bundle` have additional full Run validation sites for checkpoint/new-run/written-history work. They are not the ordinary selected Save9 Load seed path. Normal UI metadata inspection does not perform the shared full-document admission chain.

Use the existing opt-in `SceneValidationTiming` snapshot observation in `RunSnapshotSchema.validate_scene` (which already calls `finish_snapshot`). While the scope is active, capture a compact GDScript caller stack once at schema entry and attach only source/function labels to that observation. This requires no new proof, no document hash, no owner call, and no per-receipt instrumentation. First confirm `get_stack()` is populated in the cloud native debug execution; exported release builds may not provide it. If absent, use explicit labels around the small call-site set above instead.

Read the completed records alongside the existing operation scope and live-session Ready timing. They will distinguish initial admission, participant work, continuation preparation/commit, retained source loading, and journal installation without guessing which historical ordinal denotes which caller. Keep stack collection strictly opt-in; do not mix its timing with the uninstrumented matched performance result.

Profile proof is a separate nested cost: `ProfileManager.prove_scene_assignment` rereads/hashes physical Profile bytes, calls `_profile_text_validator`, canonicalizes the full validated document, then checks the assignment row. `_profile_text_validator` already caches strict parsing of exact unchanged text (up to 1 MiB), but still detaches and schema-validates the parsed document. The whole Profile is mutable even though an individual completed assignment is immutable.
