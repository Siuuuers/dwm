## 2. Product character, interpretive law, scope, and non-goals

Backup is one calm, maintained university archive cabinet. It may be rendered
in tired paper, diluted ink, soot-dark structure, and exact old-workstation
seams. It may feel overly still and slightly wrong. It may never manufacture
that unease by lying about a save, hiding or moving a record, falsifying time,
simulating corruption, or disguising technical failure as fiction.

The private mnemonic is:

> **The cabinet remembers nothing; it records exactly.**

Backup shows literal operational evidence: record identity,
`Day N · HH:MM`, `Empty`, `Unavailable`, an earlier compatible target, genuine
operation custody, or a proven result. It never explains what a record means,
identifies a speaker, gives a narrative hint, or supplies a decoding key. Save,
Load, Delete, mode selection, and confirmation are ordinary software
operations, not selectable story choices. Minesweeper results remain the sole
choice-like narrative agency under their own authority.

The inherited Four-Lens covenant is:

> **Change composition only when represented reality changes. Let object,
> position, repetition, replacement, and absence carry the evidence. Maintain
> ordinary and impossible facts with the same competent materials. Supply no
> privileged decoding key.**

The theorist names, Four-Lens label, mnemonic, semantic roles, state zones,
contrast rationale, and calibration vocabulary remain private documentation.
None appears player-facing or in assistive output.

This dossier owns:

- the nine-record player-facing registry and fixed projection;
- the cabinet, inspector, status region, dock, modes, and three host mounts;
- visible metadata, compatibility disclosure, action and confirmation grammar;
- Backup-local selection, Focus, input, scrolling, cache, status, failure, and
  recovery presentation;
- the UI consequence of Save, Load, Delete, New Acc, Logout, F5, and F9;
- captured save-time projection and palette transition;
- Standard material, component, state, authored-art, and risk mapping;
- 100, 125, and 150 percent text behavior, target masters, localization,
  assistive parity, and motion restraint; and
- proof, rejection, supersession, custody, and archive obligations.

It does not own or redesign:

- canonical snapshot contents, profile/run/branch/attempt ownership,
  anti-reroll law, challenge mechanics, or Rehearsal;
- SaveManager schema, files, raw I/O, validation, migration, checkpoint
  selection, journaling, atomicity, or recovery capability;
- lifecycle Autosave triggers or Logout transaction ordering;
- shared title, desktop, app-strip, Pause, Home/Return, route, and global
  overlay arbitration;
- cloud saves, platform accounts, import, export, file browsing, save sharing,

## 10. Save, Load, Delete, New Acc, and Logout projection

### 10.1 Save

The UI emits a semantic locator plus typed Save intent. The coordinator captures
or awaits an admissible stable canonical revision, prepares one detached
candidate, captures one save-time fact, writes atomically, rereads and validates
the durable winner, and only then republishes drawer metadata and `Saved`.

An Empty numbered record saves directly. Any occupied numbered record confirms
overwrite. Empty or readable Quick saves directly; fallback-loadable or
Unavailable Quick confirms overwrite. Autosave is lifecycle-triggered only and
its visible Save action remains disabled.

Successful Autosave is silent. A user-impacting unproven Autosave failure is
reported truthfully by the governing lifecycle or recovery surface; silence may
never be treated as proof of success. An Unavailable existing Autosave gains no
invented manual override. A later registered trigger follows the external
storage owner's non-destructive write and recovery policy.

Consent binds the exact target. If it changes, the command refreshes and asks
again. A retry of the same prepared transaction retains its captured timestamp;
a genuinely new transaction captures a new fact.

Immediate completion shows no Busy interstitial. A genuine visible-duration
local Save follows Section 12 custody. Success retains the same drawer,
publishes metadata only after durability, and then shows local `Saved`. Failure
preserves the previous record and metadata and shows exactly:

- `Couldn't save. Your previous save is unchanged.`; or
- when none existed, `Couldn't save. No save was created.`

Only real recovery actions appear.

### 10.2 Load and fallback

Load first performs a nonmutating whole-checkpoint preparation with every
restore participant. The current checkpoint is preferred. Only typed content
incompatibility may select the newest earlier fully compatible whole checkpoint
inside the same record. No fields are mixed and no live state mutates during
preparation.

Every in-run Load confirms replacement of the live continuation. In-run
fallback combines fallback disclosure and live replacement in one sheet. A
title current checkpoint passes full preparation but needs no ordinary
confirmation. Title fallback uses one fallback-only confirmation.

On activation the coordinator revalidates the bound target and commits the
atomic restore. A changed or invalid target is never substituted. Success
closes the pre-restore Backup instance and routes only after every participant
commits. Failure leaves the current game and selected record unchanged and
shows:

`Couldn't load. Your current game is unchanged.`

Title copy states only that the save could not be loaded. Failure never routes,
loads another record, or creates a run.

### 10.3 Delete

Delete exists only in Load mode and title. Every occupied record, including
Unavailable Autosave or Quick, requires confirmation bound to its exact
revision. It may delete history embedded inside that selected document but
never the separate live-run transaction or crash-recovery journal.

Success stays on the same drawer, which becomes `Empty`, and changes no live
run or other record. Failure leaves the record unchanged and shows:

`Couldn't delete. The save is unchanged.`

### 10.4 New Acc and Logout boundaries

`New Acc` is host-owned new-run and branch creation. It confirms only when a
live continuation or nonempty Autosave, including an Unavailable existing
Autosave, would be replaced. Its sheet states that Autosave will be replaced
and all other saves remain. Empty Autosave with no live continuation needs no
destructive warning. Quick and numbered records remain untouched.

Logout retains its external transaction law: confirmation Yes writes the exact
live run to Autosave and routes only after persistence is proven; No or Cancel
does neither. Failure stays in-run with explicit truthful Retry and Cancel
recovery. Logout never asks for a drawer and never changes Quick or numbered
records.

## 11. F5, F9, and the single Quick edge voice

### 11.1 Scope and target

### 11.2 F5

It supplies no direction, raw cause, compatibility detail, or explanation.

### 11.3 F9

If no immediately usable Quick target exists—including Empty or Unavailable—
the edge says only:

`Unavailable`

If preparation is blocked only by a temporary unsafe moment, it says:

`Please wait`

F9 queues no future Load. Detailed compatibility evidence remains available

### 11.4 Edge status ownership, duration, and collision

### 13.4 Conditional information overflow

ordinary Backup scroll owner.

- `thumb_h = max(8, floor(168*168/H_doc))`;
- `travel = 168-thumb_h`;
- `thumb_y = floor(travel*O/(H_doc-168))`; and
- the thumb rectangle is `(151,thumb_y,1,thumb_h)`.

Every division floors to a native integer. Nothing is fractionally placed,
resampled, or derived through a second coordinate system. The protected edge
